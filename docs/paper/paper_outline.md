### 3.2 端到端流程

按实际项目流程写：

1. 用户在风险分析页输入金融事件文本。
2. 系统抽取客户、账户、商户、设备、金额、时间和风险信号。
3. Redis 黑名单模块执行人员、关键词和高危事件过滤。
4. 未命中高危规则的事件按低风险展示，并写入 Milvus 暂存池，作为后续历史上下文。
5. 命中高危规则或风险信号的事件进入事件分类、图谱构建和风险评估。
6. 风险评估 Agent 输出多维风险分数。
7. 高风险事件触发 Milvus 历史事件回捞。
8. 通过回捞过滤的历史事件补入 Neo4j 图谱。
9. 趋势预测 Agent 生成后续风险演化和处置建议。
10. 前端展示风险等级、图谱、黑名单命中、趋势报告和复核动作。

## 4. 多智能体工作流与模型设计

本章是比赛“模型与智能体设计”的核心。

### 4.1 Agent 角色

| Agent | 输入 | 输出 | 作用 |
|---|---|---|---|
| 事件标准化 Agent | 原始金融事件文本 | 结构化事件字段 | 抽取主体、金额、时间、行为 |
| 黑名单过滤 Agent | 结构化事件 | 命中结果与处置建议 | 快速识别高危主体和关键词 |
| 事件分类 Agent | 事件文本与命中结果 | 事件类型 | 区分诈骗、洗钱、贷款欺诈等 |
| 风险评估 Agent | 事件、规则、图谱上下文 | risk_score、risk_level、维度分 | 给出可解释风险分数 |
| 图谱构建 Agent | 实体与关系 | Neo4j 节点和边 | 构建证据链 |
| 历史回捞 Agent | 高风险事件 | 相似历史事件 | 发现组合风险 |
| 趋势预测 Agent | 风险事件与图谱上下文 | 趋势报告和处置建议 | 辅助人工复核 |

### 4.2 本地模型设计

论文里可以这样写：

1. 本地 LLM 采用 Qwen3.6-35B-A3B Q6_K_M 量化版本，通过 llama.cpp 在 GPU 侧运行，用于事件理解、风险解释和趋势报告生成。
2. Embedding 模型采用 BGE M3，通过 vLLM 在 NPU 侧运行，用于事件向量化和 Milvus 相似历史召回。
3. Rerank 模型采用 BGE Reranker v2-m3，通过 vLLM 在 NPU 侧运行，用于对召回事件进行相关性排序和噪声过滤。
4. CPU 负责智能体编排、规则判断、OpenAI 兼容接口调用和数据库访问。
5. 所有模型推理默认在 AMD 本地平台执行，不上传客户隐私数据。

### 4.3 工具调用能力

## 5. 关系图谱、向量召回与风险评分方法

本章体现技术创新，建议写详细一点。

### 5.1 金融事件图谱建模

图谱节点类型：

1. Person：客户、交易对手、黑名单人员。
2. Account：银行账户、收款账户。
3. Merchant：商户、虚拟币平台、超市等。
4. Device：登录设备、新设备、共享设备。
5. Event：风险事件。
6. RiskSignal：风险信号，如分拆交易、快进快出、包装流水。

图谱关系类型：

1. TRANSFERS_TO：转账给。
2. LOGGED_IN_FROM：从设备登录。
3. MENTIONS：事件提及实体。
4. RELATED_TO：实体关联。
5. HIT_BLACKLIST：命中黑名单。
6. SIMILAR_TO：与历史事件相似。
7. INDICATES_RISK：指向风险信号。

前端图谱要求写清楚：

1. 节点名称和边名称与 Neo4j 中保存的名称一致。
2. 支持拖拽、缩放、平移、全屏。
3. 点击节点可查看标签、属性和关联边。
4. 点击边可查看关系类型、来源节点、目标节点和属性。
5. 人物图谱页面支持按客户搜索，并继续扩展节点关联。

### 5.2 Milvus 向量暂存与历史回捞

未命中高危规则的事件不直接丢弃，而是：

1. 按低风险展示。
2. 写入 Milvus 暂存池。
3. 如果同一事件重复出现，不重复写入。
4. 当后续出现高风险事件时，系统从暂存池召回相似事件。
5. 通过客户编号、账户编号、关键词和语义相似度过滤后，补入图谱。

这一设计的价值：

1. 降低低风险事件直接入图造成的噪声。
2. 保留历史上下文，便于发现组合风险。
3. 支持“先低风险、后串联为高风险”的真实金融场景。

### 5.3 多维风险评分

风险评分是 0 到 1 的连续值。

```text
risk_score = Σ dimension_score_i × weight_i
```

建议维度：

| 风险维度 | 示例信号 | 建议权重 |
|---|---|---:|
| 客户身份风险 | 黑名单客户、投诉历史、异常画像 | 0.15 |
| 交易行为风险 | 分拆交易、快进快出、异常备注 | 0.20 |
| 交易对手风险 | 涉诈账户、虚拟币平台、高危商户 | 0.20 |
| 金额频次风险 | 短期大额、多笔小额规避阈值 | 0.15 |
| 设备地域风险 | 新设备、异地登录、共享设备 | 0.10 |
| 历史上下文风险 | 相似历史事件、同账户反复出现 | 0.10 |
| 合规信号风险 | 反洗钱、贷前欺诈、监管关注词 | 0.10 |

风险等级规则：

```text
高风险：risk_score >= 0.70
中风险：0.35 <= risk_score < 0.70
低风险：risk_score < 0.35
未命中高危规则事件：按低风险展示，并暂存为历史上下文
```

注意写法：

1. 风险评估只计算一次时，后续意图识别、趋势预测和展示沿用同一个 risk_score。
2. 如果高风险触发历史回捞并完成二次风险评估，则记录 second_risk_applied，并说明分数变化原因。
3. 前端所有页面使用统一风险等级规则，避免同一事件在不同页面显示不一致。

## 6. AMD 锐龙 AI MAX+ 平台适配与异构资源利用

本章必须认真写，比赛明确要求使用 NPU 或 GPU。

### 6.1 平台特点

结合赛题描述写：

1. AMD 锐龙 AI MAX+ 395 采用 CPU、GPU、NPU 异构架构。
2. Radeon 8060S GPU 可通过 llama.cpp 承担 Q6_K_M 量化 Qwen3.6-35B-A3B 的生成式推理任务。
3. Ryzen AI NPU 可通过 vLLM 承担 BGE M3 Embedding 与 BGE Reranker v2-m3 推理任务。
4. 统一内存架构可以缓解大模型、多服务、图谱数据库和向量检索并行时的显存压力。
5. Mini AI 工作站适合银行内网、弱网或离线环境部署。

### 6.2 系统硬件分工

| 硬件 | 系统任务 | 原因 |
|---|---|---|
| CPU | FastAPI 服务、Agent 调度、规则过滤、OpenAI 兼容接口调用、SQLite/Redis/Milvus/Neo4j 访问 | 控制流复杂，适合通用逻辑 |
| GPU | llama.cpp 大模型推理、风险解释、报告生成 | 并行能力强，适合量化 LLM 的生成式推理 |
| NPU | BGE M3 Embedding、BGE Reranker v2-m3、向量化与重排 | 低功耗，适合高频文本表征和召回排序任务 |
| 统一内存 | LLM、向量库、图谱服务和前后端并行运行 | 减少显存和内存数据搬运压力 |
| SSD | 日志、向量索引、图谱和实验报告持久化 | 支持本地审计与快速恢复 |

### 6.3 本地推理部署说明

论文中建议这样描述：

1. 大模型推理采用本地部署，不调用云端模型处理客户隐私数据。
2. GPU 侧使用 llama.cpp 承载 Q6_K_M 量化后的 Qwen3.6-35B-A3B，并通过 OpenAI 兼容接口供智能体调用。
3. NPU 侧使用 vLLM 部署 BGE M3 和 BGE Reranker v2-m3，提高向量化和召回排序效率。
4. CPU 负责智能体编排、规则判断、接口调用和数据库访问，保证业务流程稳定。

## 8. 实验设计与结果分析

本章对应评分里的“性能、精度、能效”。

### 8.1 功能正确性实验

使用 `scripts/finance_demo_cases.py` 中的金融用例，覆盖正常、低风险、涉诈账户、反洗钱、贷款欺诈、重复事件等情况。

| 用例 | 场景 | 期望结果 | 需要记录 |
|---|---|---|---|
| Case 01 | 正常工资入账和消费 | 低风险、暂存 | risk_score、是否重复入库 |
| Case 02 | 普通历史交易 | 低风险、暂存 | 是否跳过后续高危流程 |
| Case 03 | 涉诈账户转账 | 高风险、命中黑名单 | 命中对象、risk_score、图谱 |
| Case 04 | 分拆转账和虚拟币归集 | 高风险、触发回捞 | 召回事件数量、二次评分 |
| Case 05 | 贷款包装流水 | 高风险或中风险 | 维度分、趋势报告 |
| Case 06 | 重复低风险事件 | 不重复写入 Milvus | 去重结果 |
| Case 07-10 | 扩展金融风险场景 | 按规则输出 | 事件类型、复核建议 |

### 8.2 风险识别效果

建议统计：

| 指标 | 含义 |
|---|---|
| 风险等级一致率 | 系统输出等级与人工标注是否一致 |
| 黑名单命中准确率 | 命中对象是否正确 |
| 历史回捞有效率 | 召回事件是否真正相关 |
| 图谱实体完整率 | 客户、账户、设备、商户是否抽全 |
| 趋势报告可用率 | 报告是否包含风险原因和处置建议 |

### 8.3 性能实验

建议做 4 组对比：

| 实验组 | 说明 |
|---|---|
| CPU 基线 | 不启用 GPU/NPU，仅 CPU 跑轻量推理或流程 |
| GPU 量化 LLM | llama.cpp + Qwen3.6-35B-A3B Q6_K_M |
| NPU 向量与重排 | vLLM + BGE M3 / BGE Reranker v2-m3 |
| GPU + NPU 协同 | GPU 做大模型推理，NPU 做向量化和召回重排 |

性能表：

| 配置 | 平均端到端延迟 | P95 延迟 | 吞吐量 | 峰值内存 | 平均功耗 |
|---|---:|---:|---:|---:|---:|
| CPU 基线 | 待填 | 待填 | 待填 | 待填 | 待填 |
| GPU 本地推理 | 待填 | 待填 | 待填 | 待填 | 待填 |
| GPU 量化模型 | 待填 | 待填 | 待填 | 待填 | 待填 |
| NPU 预筛 + GPU 推理 | 待填 | 待填 | 待填 | 待填 | 待填 |

### 8.4 精度与性能权衡

比赛要求说明“牺牲多大精度换来怎样的本地性能提升”。建议这样写：

| 模型版本 | 风险等级一致率 | 平均延迟 | 峰值内存 | 结论 |
|---|---:|---:|---:|---|
| 原始模型 | 待填 | 待填 | 待填 | 精度较高，资源占用较大 |
| INT8 量化 | 待填 | 待填 | 待填 | 精度轻微下降，延迟下降 |
| INT4 量化 | 待填 | 待填 | 待填 | 资源占用最低，需关注误报 |

写结论时可以用这个模板：

```text
在金融风控场景中，系统更重视高风险事件的召回和解释能力。量化模型带来的少量风险等级波动可以通过规则过滤、图谱证据和人工复核环节缓冲，因此在端侧部署中具有较好的性能收益。
```

### 8.5 消融实验

建议加一张消融表，体现工程设计不是堆组件：

| 方案 | 黑名单 | Milvus 回捞 | Neo4j 图谱 | 风险评分效果 |
|---|---|---|---|---|
| 仅 LLM | 无 | 无 | 无 | 解释强，但证据弱 |
| LLM + 黑名单 | 有 | 无 | 无 | 显性风险识别更快 |

## 9. 隐私安全、应用价值与未来工作

### 9.1 隐私安全设计

重点写：

1. 所有核心推理在本地 AMD 平台完成。
2. 客户事件、黑名单、向量索引、图谱和日志均可部署在企业内网。
3. Demo 数据使用 P101、P102 等脱敏编号。
4. 日志避免记录真实身份证号、银行卡号、手机号等敏感字段。
5. 后续生产化可加入登录鉴权、角色权限、操作审计、数据库加密和字段脱敏。

### 9.2 应用价值

建议写 4 点：

1. 提升风控分析员的事件研判效率。
2. 通过历史回捞和图谱补全发现组合风险。
3. 支持银行内网和弱网环境部署。
4. 可扩展到信用卡盗刷、商户套现、保险理赔、贷后预警等场景。

### 9.3 落地路径

写得具体一点：

1. 第一阶段：作为风控辅助研判工具，在内网中处理人工提交事件。
2. 第二阶段：接入交易监控系统，对高风险事件实时预警。
3. 第三阶段：接入更多业务系统，如贷款、投诉、设备指纹和商户画像。
4. 第四阶段：通过人工复核反馈持续优化评分权重和模型提示词。

### 9.4 未来工作

建议写：

1. 扩展多模态能力，例如贷款材料图片 OCR、合同/凭证识别。
2. 引入更完善的权限、审计和加密机制。
3. 增强 NPU 常驻预筛模型能力。
4. 加入批量事件分析和实时流式事件接入。
5. 与银行真实规则引擎或工单系统对接。
